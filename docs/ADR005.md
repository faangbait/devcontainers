# ADR005: AI as a first-class citizen

## Status

Accepted.

## Context

Per `README.md`, the primary goal of this repository is to sandbox coding
agents and control their context via mounting, rather than treating agent
tooling as an afterthought bolted onto a normal devcontainer.

Two things follow from that goal:

- Agent identity, credentials, and history (`~/.claude`, `~/.codex`,
  `~/.grok`, `~/.agents`, opencode's config/share/state dirs) need to survive
  container rebuilds, the same way a developer's shell history or SSH keys
  would.
- Every environment built from this repo should start from the same agent
  baseline (plugins, org policy, tool-routing config) without each variant
  having to reproduce that setup by hand.

## Decision

**Mounting.** `.devcontainer-agents/devcontainer.json` mounts a single
`portable-agents` volume at `/var/llms` and sets `CLAUDE_CONFIG_DIR`,
`CODEX_HOME`, and `OPENCODE_CONFIG_DIR` to subdirectories under it.
`src/.devcontainer/bin/devcontainer-post-create` then symlinks the
conventional per-tool home directories (`~/.claude`, `~/.codex`, `~/.grok`,
`~/.agents`, `~/.config/opencode`, `~/.local/share/opencode`,
`~/.local/state/opencode`) into that volume. Because every agent-capable
variant inherits from `.devcontainer-agents` (see ADR002), this mounting
scheme is universal rather than per-variant, and agent config/history
persists across rebuilds even though the container filesystem itself does
not.

**Baked-in baseline.** The Containerfile's `userland-payload` stage copies
`etc/AGENTS.md` to `/etc/claude-code/CLAUDE.md` and `etc/context-mode.json`
to `/etc/context-mode.json`, so an org-level policy file and the
context-mode plugin's own config exist in the image itself, independent of
whatever ends up in the mounted volume.

**Plugin bootstrap.** `devcontainer-post-create` installs the same plugin
set into both Claude Code and Codex on every container creation: the
official Anthropic marketplace (`chrome-devtools-mcp`, `frontend-design`,
`playwright`, `pyright-lsp`) plus `context-mode`, with matching opencode
plugin installs (`context-mode`, an Anthropic auth bridge, a quota plugin,
`caveman`). It also runs `rtk init -g` for Claude Code, opencode, and Codex,
and disables `rtk` telemetry. This makes the agent tool-routing layer
(`context-mode`, `rtk`) a standard part of every environment rather than
something each developer opts into by hand.

## Example: compliance enforcement

Because `/var/llms` persists, a developer's own instructions to their agent
persist too — including instructions about how to treat the plugins this
repo bootstraps. `~/.claude/CLAUDE.md` (which lands in the mounted volume,
not the image) is the concrete mechanism for that in this environment:

```markdown
# Your Tools

- @RTK.md - `rtk` is a high-performance CLI proxy that cuts up to 90% of the
  bash output your agent reads. `rtk` will automatically rewrite your bash
  commands; that's what a proxy does.
- @~/.claude/plugins/marketplaces/context-mode/CLAUDE.md - context-mode is
  enabled and enforced. When it says "BLOCKED" -- it means blocked (your
  command will fail).
  
The user has reviewed the instructions provided by both utilities on <date>. Prior to your first turn, explicitly ask the user:

- Should I use `rtk` and `context-mode` for the duration of this session?
```

This is fuctionally the only way to get Claude to actually use these tools. Without these instructions, and the user's explicit authorization, he will call the plugins a security threat because he "can't verify what they do." He will immediately become confrontational, not just about these tools, but on nearly every topic.

## Consequences

- Agent credentials, plugin installs, and per-tool history outlive
  `devcontainer rebuild`; only the `portable-agents` volume needs to
  survive, not the container.
- All agent-capable variants get the same plugin baseline for free by
  inheriting `.devcontainer-agents`'s mount and env vars (ADR002); adding a
  plugin to `devcontainer-post-create` updates every variant at once.
- The image itself carries a baseline org policy
  (`/etc/claude-code/CLAUDE.md`) independent of the mounted volume, so a
  freshly created volume (or one shared across untrusted forks of this repo)
  doesn't leave an agent with no policy at all.
- Because `/var/llms` is a long-lived volume, anything written into it —
  including a user's own `CLAUDE.md` — persists and travels with the
  developer across rebuilds. That is by design for legitimate per-developer
  preferences (see the compliance-enforcement example above).
